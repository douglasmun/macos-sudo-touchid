# Security Audit Summary

This document captures the security review expectations for publishing this repository. It intentionally avoids local usernames, hostnames, private paths, and machine-specific logs.

## Scope

Reviewed surfaces:

- PAM configuration generated by `scripts/install.sh`.
- Source build path in `scripts/build-pam-reattach.sh`.
- Runtime audit checks in `scripts/audit.sh`.
- Uninstall behavior in `scripts/uninstall.sh`.
- Public documentation and release checklist.

Out of scope:

- Upstream source audit of `pam_reattach`.
- Apple's `pam_tid.so`, `sudo`, and PAM implementations.
- Enterprise policy suitability for managed fleets.

## Security Invariants

The repository is designed around these invariants:

- Do not edit or replace `/etc/pam.d/sudo`.
- Configure sudo only through `/etc/pam.d/sudo_local`.
- Do not load `pam_reattach.so` directly from Homebrew, the Cellar, or any user-writable package-manager path.
- Copy the active `pam_reattach.so` module to `/usr/local/lib/pam/pam_reattach.so`.
- Ensure the active PAM module path and parent directories are `root:wheel` and not group/other writable.
- Keep `pam_reattach` as `optional`.
- Keep `pam_tid` as `sufficient`.
- Use `ignore_ssh` by default.
- Preserve password fallback through Apple's normal sudo PAM stack.

## Current Expected PAM Configuration

```pam
auth       optional       /usr/local/lib/pam/pam_reattach.so ignore_ssh
auth       sufficient     pam_tid.so
```

`pam_reattach` is optional because it should prepare the GUI session for later modules, not authenticate the user by itself. `pam_tid` is sufficient so a successful Touch ID check can satisfy sudo authentication, while failure falls through to the remaining password path.

## Reviewed Edge Cases

- Missing or broken `pam_reattach.so` should not authenticate the user.
- Direct Homebrew/Cellar module loading is rejected by design.
- Symlinked active PAM config or module paths are rejected by audit/install checks.
- Group/other-writable active PAM paths are rejected by audit/install checks.
- Existing unmanaged active `sudo_local` rules are not overwritten silently.
- Uninstall does not delete `sudo_local`; it replaces it with a safe comment-only file.
- Reinstall after uninstall is documented as requiring an interactive Terminal or another visible password prompt path.

## Validation Commands

Run before release:

```sh
./scripts/check.sh
```

Run after install:

```sh
./scripts/audit.sh
```

The source-build path should also be tested before tagging a release:

```sh
./scripts/build-pam-reattach.sh
./scripts/install.sh
./scripts/audit.sh
```

## Residual Risks

- This is a convenience feature, not a system hardening control.
- Biometric prompts can create prompt-confusion risk if users approve prompts without understanding which command triggered them.
- This is not recommended for shared-admin, kiosk, lab, remote-admin, or high-assurance environments.
- The source build pins and verifies an upstream release tarball, but users still trust the upstream project and local compiler toolchain.

## Release Recommendation

Ready for an initial public release once the release checklist is completed on a clean test machine.
